# Release hardening plan

Goal: close the reliability and security gaps found before the next major release, without adding
logging, log upload or telemetry. Branch: `perf/analytics-and-service-reliability`. The orchestrator
ticks items as they land; workers do not edit this file. Finished work lives in git history.

## 1. Work queue

- [ ] 1.1 One BitGit process per data directory
- [ ] 1.2 Git service survives a stray promise rejection
- [ ] 1.3 Frontend reports unhandled errors instead of dropping them
- [ ] 1.4 Content Security Policy (own commit, last)

## 2. Decisions that constrain the work

### 2.1 Instance guard is keyed on the data directory

The resource two processes corrupt is the data directory (`projects.json`, settings, vault), not the
executable: `docs/NATIVE_RECOVERY.md` records that the cache lock is in-process only. The guard is
therefore an exclusively opened lock file inside `app_data::config_dir()`, held for the life of the
process. The operating system releases it when the process dies, so a crash leaves no stale lock.

A guard keyed on the application identifier (the Tauri single-instance plugin) was rejected: it would
block a debug smoke run on an isolated `BITGIT_TEST_DATA_DIR` whenever the installed app is open, and
it adds a git dependency before a release. The second process tells the user BitGit is already running
and exits; it does not try to find and focus the first window.

### 2.2 A stray rejection is reported, an uncaught exception still exits

Every command already runs inside `handleCommand`'s try/catch, so an `unhandledRejection` is a
background promise outside any request. Exiting would kill other repositories' running pushes for a
failure that touched none of them, so the service reports it on stderr, redacted, and continues.
`uncaughtException` keeps exiting: state is unknown there, and Rust restarts the service on the next
request.

### 2.3 Frontend handlers surface, deduplicate, and never block

`unhandledrejection` and `error` show one toast per distinct message (the message is the toast id, so
a failing poll replaces its toast rather than stacking) and write to the console. Nothing is persisted
or sent anywhere.

### 2.4 CSP is verified against a built app, not the dev server

Tauri 1 applies `security.csp` to the dev server too unless `security.devCsp` is set, and Vite's
React refresh preamble is an inline script, so `devCsp` needs its own permissive policy. A dev run
therefore proves nothing about the release policy: verification is a `tauri build --debug` binary
started with an isolated `BITGIT_TEST_DATA_DIR`. It lands as its own commit so it can be reverted alone.

## 3. Descoped

- Code splitting: the 447 KB bundle loads from local disk, not a network. No measured startup cost
  justifies lazy routes and their loading states.
- `setGithubToken` race between concurrent remote recoveries: recorded in `docs/NATIVE_RECOVERY.md`
  with its remedy; it changes the recovery request contract and is its own task.
